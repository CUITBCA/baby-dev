# 链协任务平台技术选型说明（框架为主）

## 1. 目标
这份文档只回答一件事：这套“任务提交 + AI 审核 + 发凭证”系统，主要用什么框架来做，以及为什么。

## 2. 总体结论（推荐栈）

- 前端框架：`Next.js 15`（React + TypeScript）
- 后端框架：`NestJS`（Node.js + TypeScript）
- 数据库：`PostgreSQL`
- ORM：`Prisma`
- 队列：`BullMQ + Redis`
- AI 审核集成：`OpenClaw`（通过后端异步任务调用）
- Webhook 来源：`GitHub Webhook`
- 合约交互：`viem`（可替代 ethers.js）
- 部署：
- 前端 `Vercel`
- 后端 `Railway/Render/Fly.io`（任选一个）
- 数据库 `Neon/Supabase Postgres`
- 对象存储（可选）`Cloudflare R2`

---

## 3. 为什么是这套框架

## 3.1 前端用 Next.js
- 你后续会有管理后台 + 学员端两个界面，Next.js 路由和工程组织更清晰。
- 同时支持 SSR/CSR，首屏和 SEO 需要时可直接用。
- 与 Vercel 配合最省心，部署和回滚快。
- TypeScript 生态成熟，适合长期维护。

## 3.2 后端用 NestJS
- 你要做的是“流程型系统”（提交、审核、发证、状态流转），NestJS 的模块化和依赖注入更适合复杂业务。
- 原生支持守卫、拦截器、DTO 校验，权限和审计更规范。
- 与 BullMQ/Redis 集成顺畅，天然适合 webhook 异步处理和 AI 任务队列。

## 3.3 数据层用 PostgreSQL + Prisma
- 关系数据明显（用户、任务、提交、审核、凭证）适合关系型数据库。
- Prisma 开发效率高，迁移可控，类型提示好。
- 后续做统计报表也方便。

## 3.4 异步层用 BullMQ + Redis
- GitHub webhook 可能有突发流量，必须异步削峰。
- AI 调用耗时不可控，放进队列可重试、可追踪、可告警。
- 失败任务可人工重跑，不阻塞主流程。

## 3.5 AI 审核用 OpenClaw + 人工兜底
- AI 适合做“初筛 + 结构化评分”，能大幅减少人工工作量。
- 最终可配置为“AI 建议 + 人工终审”，避免误判争议。
- 通过 webhook 自动触发，体验上接近 CI 流程。

---

## 4. 架构分层（建议）

- `apps/web`：Next.js 前端（学员端 + 管理端）
- `apps/api`：NestJS 后端 API
- `apps/worker`：NestJS/BullMQ Worker（处理 webhook、AI 审核、发证任务）
- `packages/shared`：共享类型、验证规则、常量

可先单仓库，后面再演进成 monorepo（pnpm workspace）。

---

## 5. 与你场景强相关的关键框架能力

## 5.1 GitHub Webhook
- 入口：`POST /api/integrations/github/webhook`
- 框架要点：
- NestJS Controller 接收事件
- 中间件校验 `X-Hub-Signature-256`
- 通过 `delivery_id` 做幂等
- 投递到 BullMQ 队列异步处理

## 5.2 OpenClaw 审核任务
- Worker 消费 webhook 任务后：
- 拉取仓库变更上下文
- 根据任务 rubric 组装 prompt
- 调 OpenClaw 获取 `score/decision/issues`
- 回写 PostgreSQL（submission + ai_review + log）

## 5.3 凭证发放
- 审核通过后触发发证任务
- 如果上链：
- 用 `viem` 调用合约
- 记录 `txHash` 和重试状态
- 如果先站内发证：
- 生成 `credential_id` + 可验证页面

---

## 6. 不推荐的首期方案

- 前端用纯原生 HTML/JS：迭代慢，后台复杂后维护成本高
- 后端用 Express 裸写全流程：初期快，后期权限/流程/测试会失控
- webhook 同步处理 AI：请求超时和失败率高

---

## 7. 首期版本建议（2-3 周可落地）

2. Week 2：GitHub webhook + BullMQ + OpenClaw AI 评分回写
