## 2. 文档目标

把以上技术任务体系化为“可报名、可提交、可验证、可发凭证”的平台，供链协同学参与。  
同学完成任务并通过验证后，系统自动/半自动发放凭证（链上或站内凭证）。

---

## 3. 业务范围与角色

## 3.1 角色
- 学员（链协同学）：报名、查看任务、提交成果、查看验证结果和凭证
- 审核员（技术部/助教）：审核提交内容、发起复核、处理异常
- 管理员：配置任务、配置规则、管理批次、查看统计、管理凭证模板

## 3.2 业务对象
- 训练营批次（Cohort）
- 任务（Task）
- 提交记录（Submission）
- 验证结果（Verification）
- 凭证（Credential）

---

## 4. 业务流程（端到端）

1. 管理员创建训练营批次与任务清单（对应图片中 1-9 项）。
2. 学员使用钱包地址 + GitHub 账号报名。
3. 学员按任务提交材料（仓库链接、合约地址、演示链接、文档等）。
4. 系统执行自动验证（如仓库可访问、合约部署存在、前端链接可达）。
5. 自动验证未通过或需人工判断项进入审核员人工审核。
6. 通过后记录完成状态，累计学员完成度。
7. 达到发证条件后，系统生成并发放凭证。
8. 学员可在个人页查看凭证、验证明细和失败原因。

## 5. 功能需求 - 前端

## 5.1 通用要求
- Web 端，优先移动端适配
- 登录方式：钱包签名登录（必选）+ GitHub 绑定（必选）
- 中英文可扩展（首期可先中文）

## 5.2 页面清单
- 首页：项目介绍、批次信息、报名入口
- 任务列表页：展示任务状态（未开始/进行中/待审核/已通过/未通过）
- 任务详情页：任务说明、提交格式、验证规则、截止时间
- 提交页：按任务类型提交表单 + 附件（链接为主）
- 个人中心：进度、失败原因、重提入口、凭证展示
- 管理后台：
- 批次管理
- 任务配置
- 提交审核
- 凭证模板和发放
- 数据看板

## 5.3 学员侧功能
- 报名：填写钱包地址、GitHub 用户名、基本信息
- 任务提交：
- 支持多类型字段（URL、文本、地址、文件链接）
- 支持多次提交（保留历史版本）
- 状态追踪：可看到自动验证日志与人工审核意见
- AI 评审结果：展示 AI 评分、评语、失败点、建议修复项
- 凭证查看：支持复制凭证 ID、跳转链上浏览器（如是链上）

## 5.4 管理侧功能
- 任务模板化（从“技术部任务 1-9”快速生成）
- 任务维度配置：
- 必填字段
- 自动验证规则
- 是否需要人工审核
- 截止时间
- 审核操作：通过/驳回/要求补充材料
- AI 评审配置：
- Prompt 模板版本管理
- 通过阈值（如 70 分）
- 触发策略（push、PR merge、手动重跑）
- 模型开关（仅 AI / AI+人工）
- 发证规则配置：
- 全部任务通过发证
- 或达到指定积分发证

## 5.5 前端验收标准
- 学员可在 10 分钟内完成报名与首次提交
- 状态更新延迟 < 5 秒（提交后页面刷新可见）
- 关键页面移动端可用（375px 宽度无布局错乱）

## 6. 功能需求 - 后端

## 6.1 服务边界
- 用户与认证服务
- 任务与提交服务
- 验证服务（自动验证）
- 审核与流程服务
- 凭证发放服务
- 通知服务（站内 + 邮件/飞书可扩展）

## 6.2 核心能力
- 鉴权：钱包签名校验、JWT 会话管理、RBAC 权限控制
- 提交流程：
- 创建提交
- 触发自动验证（含 AI 评审）
- 写入验证日志
- 流转状态
- 审核流程：
- 审核员领取待审任务
- 审核结果回写
- 触发重提/通过
- 发证流程：
- 判断发证条件
- 调用凭证铸造或生成站内证书
- 记录 txHash / credentialId

## 6.3 自动验证规则（首期建议）
- GitHub 仓库可访问且非空
- ERC20/ERC721 合约地址在测试网可查
- 前端部署地址（Vercel）可访问且返回 200
- Node.js 后端 API 存活检查（健康检查接口）
- UniswapV2 学习项：提交对比说明文档（自动检查关键词 + 人工复核）
- 代码任务启用 AI 评审：基于仓库提交内容进行规则打分与结论判断

## 6.4 状态机
- Submission 状态：
- `draft`
- `submitted`
- `ai_reviewing`
- `ai_review_failed`
- `auto_check_failed`
- `pending_manual_review`
- `approved`
- `rejected`
- Credential 状态：
- `not_eligible`
- `eligible`
- `issuing`
- `issued`
- `issue_failed`

## 6.5 后端验收标准
- 单条提交创建接口 P95 < 300ms（不含异步验证）
- 自动验证任务 1 分钟内开始执行
- 凭证发放成功率 >= 99%（排除链拥堵）
- AI 评审回调入库成功率 >= 99.9%

## 6.6 OpenClaw + GitHub Webhook AI 评审方案

### 6.6.1 触发方式
- 学员在报名时绑定 GitHub 账号与仓库
- 系统为每个任务生成唯一回调密钥（webhook secret）
- 学员仓库配置 GitHub Webhook，事件至少包含 `push`、`pull_request`（可选）
- GitHub 事件推送到平台后端 `/api/integrations/github/webhook`

### 6.6.2 评审流程
1. 后端校验签名（`X-Hub-Signature-256`）并去重（delivery id）。  
2. 根据仓库、分支、commit 映射到对应学员和任务。  
3. 触发 OpenClaw 评审任务，传入仓库地址、commit sha、任务 rubric、Prompt 模板。  
4. OpenClaw 返回结构化结果：分数、是否通过、问题列表、证据片段。  
5. 后端写入 `ai_reviews` 与 `verification_logs`，更新 submission 状态。  
6. 若低置信度或边界分数，自动进入人工复核队列。  

### 6.6.3 通过判定规则（建议）
- 总分 >= 阈值（默认 70）
- 关键项必须通过（如“有可运行代码”“测试网合约可验证”）
- 如果 AI 结果为 `uncertain`，必须人工审核
- 连续 2 次 AI 失败后，必须阅读失败原因并重提

### 6.6.4 安全与风控
- webhook 签名校验 + IP 白名单（可选）
- 幂等处理：同一 delivery id 只处理一次
- 评审输入脱敏（去除 token、私钥）
- 保留 Prompt、模型版本、输出快照，支持事后审计

### 6.6.5 人工兜底策略
- AI 仅作“初筛 + 建议”，最终裁决可配置为人工优先
- 管理员可一键改判并记录理由
- 支持“申诉”流程：学员提交说明后进入二审

## 7. 数据模型（简版）

- `users`
- `id`, `wallet_address`, `github_username`, `role`, `created_at`
- `cohorts`
- `id`, `name`, `start_at`, `end_at`, `status`
- `tasks`
- `id`, `cohort_id`, `title`, `description`, `rules_json`, `required`, `order_no`
- `submissions`
- `id`, `task_id`, `user_id`, `content_json`, `status`, `version`, `submitted_at`
- `verification_logs`
- `id`, `submission_id`, `check_type`, `result`, `message`, `raw_json`
- `ai_reviews`
- `id`, `submission_id`, `provider`, `model`, `prompt_version`, `score`, `decision`, `confidence`, `issues_json`, `created_at`
- `reviews`
- `id`, `submission_id`, `reviewer_id`, `decision`, `comment`, `reviewed_at`
- `credentials`
- `id`, `user_id`, `cohort_id`, `credential_type`, `status`, `tx_hash`, `issued_at`

## 9. 非功能需求

- 安全：
- 钱包签名防重放（nonce 一次性 + 过期）
- 提交链接白名单校验（防注入）
- 管理后台全链路审计日志
- webhook 签名校验失败告警与封禁策略
- 可观测性：
- 接口日志、异步任务日志、失败告警
- AI 评审链路追踪（webhook -> queue -> OpenClaw -> 回写）
- 可扩展性：
- 验证规则插件化（后续可接更多链和任务类型）
- AI provider 可插拔（OpenClaw / 其他模型服务）
